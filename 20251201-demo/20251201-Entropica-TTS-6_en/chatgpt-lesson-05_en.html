1. QEC Research Workflow and the Role of el-loom

1.1 Typical QEC Research Problems

Common research questions in the QEC field at the PhD and advanced-research level include:

  • Designing new stabilizer codes tailored to specific hardware constraints (coupling graph, decoherence mechanisms, measurement frequency).
  • Re-evaluating thresholds of known codes (e.g., surface code, color code) under asymmetric noise or realistic hardware noise.
  • Studying the performance of new types of decoders (neural decoder, tensor-network decoder, belief propagation, etc.).
  • Designing custom measurement schedules and gate schedules, and analyzing the impact of rounding errors and time-correlated noise.
  • Comparing different code families in terms of asymptotic scaling of the logical error rate.

These problems share a common requirement: to rapidly and systematically turn “abstract code structure + noise model” into “reproducible numerical experiments.” The el-loom package is a Python toolkit designed exactly for this purpose, with an emphasis on:

  • A unified abstraction for stabilizer codes and measurement circuits.
  • Integration with efficient simulators such as stim for large-scale Monte Carlo simulations.
  • Support for multiple decoders and output formats, facilitating downstream data analysis.

2. From Mathematical Form to el-loom Data Structures: Custom Stabilizer Codes

2.1 Mathematical Definition of a General Stabilizer Code

A stabilizer code is defined on \(n\) physical qubits, with stabilizer group \(S\) an abelian subgroup of the \(n\)-qubit Pauli group that does not contain \(-I\). Let \(S = \langle S_1,\dots,S_{n-k} \rangle\); then its codespace is \[ \mathcal{C} = \{ \lvert \psi \rangle \in (\mathbb{C}^2)^{\otimes n} : S_i \lvert \psi \rangle = \lvert \psi \rangle,\, \forall i \} . \] If the generators of \(S\) are linearly independent (in the Pauli group modulo \(\pm 1\)), then the code encodes \(k = n - \text{rank}(S)\) logical qubits.

Logical Pauli generators can be chosen as \[ \{ \overline{X}_1,\dots,\overline{X}_k,\overline{Z}_1,\dots,\overline{Z}_k \} \] such that:

  • \([ \overline{X}_i, \overline{Z}_j ] = 0\) for \(i \neq j\),
  • \(\{ \overline{X}_i, \overline{Z}_i \} = 0\) (they anticommute),
  • for all \(i,j\), \([\overline{X}_i, S_j] = [\overline{Z}_i, S_j] = 0\).

2.2 Pauli Vector Representation and Binary Matrix Form

In implementations, we often use the binary symplectic representation to represent Paulis: \[ P = i^\kappa X^{\mathbf{a}} Z^{\mathbf{b}} \quad \leftrightarrow \quad (\mathbf{a} \mid \mathbf{b}) \in \mathbb{F}_2^{2n}, \] where \(\mathbf{a},\mathbf{b} \in \mathbb{F}_2^n\); for the \(j\)-th qubit, if the operator is \(X\) then \(a_j=1,b_j=0\); if \(Z\), then \(a_j=0,b_j=1\); if \(Y\), then \(a_j=b_j=1\); and if \(I\), then \(a_j=b_j=0\).

The (anti-)commutation relation between two Paulis \(P,Q\) is determined by the symplectic inner product: \[ P Q = (-1)^{\langle P,Q\rangle} Q P, \] where \[ \langle (\mathbf{a}\mid\mathbf{b}), (\mathbf{c}\mid\mathbf{d}) \rangle = \mathbf{a}\cdot\mathbf{d} + \mathbf{b}\cdot\mathbf{c} \in \mathbb{F}_2. \]

Thus a stabilizer code can be represented by a \((n-k) \times 2n\) binary matrix \[ H_S = [A\mid B] \] where each row corresponds to the Pauli vector representation of one stabilizer generator.

2.3 Core Concepts for Defining Custom Codes in el-loom

In el-loom, the core abstraction is not just a static \(H_S\), but rather:

  1. Geometric/topological data: qubit locations, adjacency relations, and hierarchical structure (e.g., lattice, tiling).
  2. Pauli structure of stabilizers and logical operators: which can be viewed as the algebraic layer.
  3. Measurement circuits and schedules: how these stabilizers are measured in time.

Concretely in Python, a typical workflow (written as pseudo-code) is: 


from loom import codes, circuits, layouts

# 1. Define qubit layout (can be 1D, 2D, graph-based)
layout = layouts.CustomLayout(qubits=range(n), connectivity=edges)

# 2. Define stabilizers and logical Pauli operators
stabilizers = [
    "X0 X1 X3 X4",  # textual Pauli representation
    "Z1 Z2 Z4 Z5",
    # ...
]
logical_x = ["X0 X2 X4", ...]
logical_z = ["Z1 Z3 Z5", ...]

code = codes.StabilizerCode(
    n_qubits=n,
    stabilizers=stabilizers,
    logical_x=logical_x,
    logical_z=logical_z,
    layout=layout,
)

# 3. Construct syndrome measurement circuit from the code
meas_circuit = circuits.SyndromeMeasurementCircuit.from_code(code)

Please refer to the official documentation for the actual API names; the above example only illustrates the “level of abstraction.” The core ideas are:

  • You should explicitly encode the mathematical specification of your custom code (stabilizers and logical operators).
  • The geometry (layout) is used to enforce locality constraints and construct schedules.
  • The circuit abstraction is used for inserting noise and running simulations subsequently.

3. From Mathematical Design to a Concrete Example: A Custom Small Topological Code

3.1 Example: A Small 9-Qubit Planar Surface Code

For demonstration, we consider a simplified 9-qubit planar surface code patch. The physical qubits are arranged in a \(3\times3\) grid: 

q0  q1  q2
q3  q4  q5
q6  q7  q8

For this simplified example, we design 4 \(Z\)-type plaquette stabilizers and 4 \(X\)-type star stabilizers (for illustration, we adopt a slightly non-standard but structurally clear version).

  • \(Z\)-type stabilizers (acting on plaquettes): \[ S^{(Z)}_1 = Z_0 Z_1 Z_3 Z_4,\quad S^{(Z)}_2 = Z_1 Z_2 Z_4 Z_5, \] \[ S^{(Z)}_3 = Z_3 Z_4 Z_6 Z_7,\quad S^{(Z)}_4 = Z_4 Z_5 Z_7 Z_8. \]
  • \(X\)-type stabilizers (acting on vertex stars): \[ S^{(X)}_1 = X_0 X_1 X_3 X_4,\quad S^{(X)}_2 = X_1 X_2 X_4 X_5, \] \[ S^{(X)}_3 = X_3 X_4 X_6 X_7,\quad S^{(X)}_4 = X_4 X_5 X_7 X_8. \]

Clearly, all \(Z\)-type stabilizers commute with each other, as do all \(X\)-type stabilizers, and any \(X\)-type stabilizer overlaps with any \(Z\)-type stabilizer on an even number (0, 2, or 4) of qubits, so they commute as well. There are 8 independent generators, but multiplicative relations among them may lead to \(\text{rank} < 8\); assuming the rank is 8, then \[ k = n - \text{rank}(S) = 9 - 8 = 1, \] so this is a \([[9,1,d]]\) code. The minimum distance \(d\) is about 3 (corresponding to string-like logical operators crossing the patch).

3.2 Binary Symplectic Check and Distance Estimation

Convert the 8 stabilizers above into Pauli vectors to build \(H_S\): \[ H_S = \begin{bmatrix} \mathbf{a}^{(X)}_1 & \mathbf{b}^{(X)}_1\\ \vdots & \vdots\\ \mathbf{a}^{(X)}_4 & \mathbf{b}^{(X)}_4\\ \mathbf{a}^{(Z)}_1 & \mathbf{b}^{(Z)}_1\\ \vdots & \vdots\\ \mathbf{a}^{(Z)}_4 & \mathbf{b}^{(Z)}_4 \end{bmatrix} \in \mathbb{F}_2^{8\times 18}. \]

For any candidate logical Pauli \(L = (\mathbf{a}_L\mid\mathbf{b}_L)\), it must satisfy:

  1. \(L\) commutes with all stabilizers: \[ H_S \, J \, L^\top = \mathbf{0} \quad\text{(mod 2)}, \] where \[ J = \begin{bmatrix} 0 & I_n\\ I_n & 0 \end{bmatrix} \in \mathbb{F}_2^{2n\times 2n}. \]
  2. \(L\) is not in the stabilizer group (modulo phase), i.e., \(L \notin \text{row-span}(H_S)\).

The distance \(d\) is the minimal Pauli weight among all non-stabilizer logical Paulis: \[ d = \min_{L \in N(S)\setminus S} \mathrm{wt}(L), \] where \(N(S)\) is the normalizer.

In practice, efficient binary linear algebra (implemented in numpy or rust, for example) can be used to search all Paulis of weight \(\le d_{\max}\) and check whether they are in the normalizer and are not stabilizers. el-loom typically provides functionality such as:

  • Given a StabilizerCode structure, automatically computing \(k\), estimating the distance, etc.
  • Interoperability with external libraries (such as qecsim, stim).

4. Rigorous Modeling of Noise Models and Temporal Structure

4.1 Abstraction of Noise Channels and the Local Noise Assumption

In QEC theoretical analysis, we usually assume local stochastic noise. Within a single time step (time slice), every controlled physical operation (gate, measurement, idle) may be accompanied by an independent noise channel: \[ \mathcal{E}(\rho) = (1-p)\rho + \sum_i p_i E_i \rho E_i^\dagger, \] often simplified to:

  • Single-qubit depolarizing: \[ \mathcal{D}_p(\rho) = (1-p)\rho + \frac{p}{3}(X\rho X + Y\rho Y + Z\rho Z). \]
  • Two-qubit depolarizing: \[ \mathcal{D}^{(2)}_p(\rho) = (1-p)\rho + \frac{p}{15}\sum_{P\in\mathcal{P}_2\setminus\{II\}} P\rho P^\dagger. \]
  • Asymmetric noise (\(p_X \neq p_Z\)): \[ \mathcal{E}(\rho) = (1-p_X-p_Z)\rho + p_X X\rho X + p_Z Z\rho Z. \]

In more realistic hardware scenarios, one may also consider non-Pauli noise such as amplitude damping, dephasing, and crosstalk. Under the Pauli twirling approximation, it is common to approximate such noise by a Pauli channel to interface conveniently with Pauli simulators like Stim.

4.2 Specifying Noise Models in el-loom

In el-loom, a “noise rule set” is typically used to describe:

  • Which kind of gate/measurement/idle operation it applies to.
  • The probabilistic parameters (a single scalar \(p\) or multiple parameters \((p_X,p_Z,\dots)\)).
  • Whether it is time-correlated (correlated across cycles).

Conceptual example: 


from loom import noise

noise_model = noise.NoiseModel()

# Single-qubit gate depolarizing
noise_model.add_gate_noise(
    gate_type="H",
    noise="depolarizing",
    p=1e-3,
)

# Two-qubit depolarizing noise on CNOT
noise_model.add_gate_noise(
    gate_type="CNOT",
    noise="two_qubit_depolarizing",
    p=2e-3,
)

# Measurement error
noise_model.add_measurement_noise(
    basis="Z",
    p_meas=5e-3,
)

In relation to theoretical analysis, we would like to ensure that the noise channel in the model, \(\mathcal{E}_{\text{hardware}}\), is close in diamond norm to the theoretical noise assumption \(\mathcal{E}_{\text{theory}}\): \[ \|\mathcal{E}_{\text{hardware}} - \mathcal{E}_{\text{theory}}\|_\diamond \ll 1, \] or at least that the approximations used (such as Pauli twirling) are clearly documented in the experimental design.

4.3 Temporal Structure and Cycles

QEC is typically organized in cycles: each cycle executes one complete syndrome measurement sequence. Starting from a logical state \(\rho_L\), after \(T\) cycles we have: \[ \rho_L^{(T)} = (\mathcal{R}\circ\mathcal{M}\circ\mathcal{N})^T (\rho_L), \] where:

  • \(\mathcal{N}\): the actual noise channel (including gate noise and idle noise).
  • \(\mathcal{M}\): syndrome measurement and classical post-processing (decoder input).
  • \(\mathcal{R}\): the recovery operator output by the decoder.

In the design of el-loom, this is implemented via a “repeated circuit” or “cycle template”: 


from loom import circuits

cycle_circuit = circuits.SyndromeMeasurementCircuit.from_code(code)

# Add noise
noisy_cycle = cycle_circuit.with_noise(noise_model)

# Repeat T times
T = 100
full_circuit = noisy_cycle.repeat(T)

Such time-structured circuits can be passed to low-level simulators like Stim, which then provide statistics on logical errors after long-time evolution.

5. Measurement Circuit Design and Error Propagation Analysis

5.1 CNOT-Based Syndrome Extraction

For a stabilizer \(S = \bigotimes_{j=1}^n P_j\) (where \(P_j\in\{I,X,Y,Z\}\)), a typical syndrome measurement circuit is:

  1. Introduce an ancilla qubit \(a\), initialized to \(\lvert 0\rangle_a\) (for \(Z\)-type) or \(\lvert + \rangle_a\) (for \(X\)-type).
  2. For \(Z\)-type:
    • For each physical qubit \(j\) with \(P_j=Z\), apply \(\mathrm{CNOT}(j \rightarrow a)\).
    • Finally, measure the ancilla in the \(Z\) basis to obtain the syndrome bit.
  3. For \(X\)-type:
    • If the ancilla is in \(\lvert + \rangle\), then use \(\mathrm{CNOT}(a \rightarrow j)\) for each \(P_j=X\).
    • Finally, measure the ancilla in the \(X\) basis.

We can write the measurement operator for the Z-type case in a formal way: \[ M_S = \sum_{s=\pm 1} s \, \Pi_s, \] where \[ \Pi_s = \frac{1}{2}(I + sS) \] is the projector onto the eigenspace of \(S\) with eigenvalue \(s\), implemented by the ancilla’s evolution and measurement. The key to error propagation lies in the Heisenberg picture of CNOT:

  • Under \(\mathrm{CNOT}(c\rightarrow t)\): \[ X_c \mapsto X_c X_t,\quad Z_c \mapsto Z_c,\quad X_t \mapsto X_t,\quad Z_t \mapsto Z_c Z_t. \]

Thus an \(X\) error on the ancilla can propagate through the CNOT to all target qubits, and vice versa. This is why syndrome-circuit scheduling and ancilla reuse can strongly affect the structure of correlated errors.

5.2 Custom Measurement Schedules in el-loom

el-loom typically provides two strategies:

  1. Automatically generated schedules: Based on the supports of stabilizers and the layout, it attempts to generate conflict-free circuits with minimal depth.
  2. Manually specified schedules: Researchers can explicitly define multiple rounds of CNOTs and ancilla usage to finely control the structure of error propagation.

An example of manual specification: 


from loom import circuits

builder = circuits.CircuitBuilder(code)

# Design a measurement circuit for some Z-type stabilizer S_1
anc = builder.new_ancilla(init="0")

# round 1: CNOTs on disjoint pairs
builder.cnot(control=0, target=anc)  # Z on data 0
builder.cnot(control=3, target=anc)  # Z on data 3

# round 2: next layer
builder.cnot(control=1, target=anc)
builder.cnot(control=4, target=anc)

# measure ancilla in Z
builder.measure(anc, basis="Z")

syndrome_circuit = builder.to_circuit()

Using such a builder interface, you can:

  • Avoid multiple ancillas simultaneously interacting with neighboring qubits (reducing correlated errors).
  • Optimize circuit depth (taking into account T1/T2 decoherence).
  • Insert idle-gate noise models.

This “local stabilizer measurement circuit” can then be replicated for all faces/stars to form a complete cycle.

6. Decoding and Monte Carlo Simulation: From Syndromes to Logical Error Rates

6.1 Mathematical Structure of Syndromes and Error Classes

Given a Pauli error \(E\), its syndrome \(s(E) \in \mathbb{F}_2^{n-k}\) is defined as \[ s_i(E) = \begin{cases} 0, & \text{if } [E, S_i] = 0,\\ 1, & \text{if } \{E, S_i\} = 0, \end{cases} \] or equivalently \[ s(E) = H_S J E^\top \in \mathbb{F}_2^{n-k}, \] where \(E\) is represented as a binary symplectic vector.

In essence, a decoder is a map \[ \mathcal{D}: \mathbb{F}_2^{n-k} \to \mathcal{P}_n / S, \] which, given a syndrome, outputs an equivalence class of recovery operators \(R\). The logical error rate of interest is the probability that \(R E \notin S\) (i.e., a nontrivial logical error occurs).

6.2 Monte Carlo Estimation of the Logical Error Rate

Assume the noise strength per cycle is \(p\). We are interested in \[ p_L(p, d, T) = \Pr[\text{logical error after } T \text{ cycles}]. \] The Monte Carlo procedure is:

  1. Randomly sample noise instances \(E^{(t)}\) for each cycle \(t\).
  2. Propagate them through the measurement circuit to obtain a sequence of syndromes \(\{s^{(t)}\}\).
  3. Feed \(\{s^{(t)}\}\) into the decoder \(\mathcal{D}\) to obtain the recovery operations \(\{R^{(t)}\}\) for each cycle.
  4. The final effective logical error operator \(L_{\text{eff}}\) is the combination of all noise and recovery operations; we check whether it acts as a nontrivial Pauli in the logical subspace.

Using the law of large numbers, we estimate \[ \hat{p}_L = \frac{N_{\text{logical error}}}{N_{\text{trials}}} \] and sample over different \(p\) and \(d\) to perform threshold analysis.

6.3 Setting Up Decoders and Simulation Workflows in el-loom

el-loom supports several ways of attaching decoders, including:

  • Built-in minimum-weight perfect matching (MWPM) or Union-Find decoders.
  • Interoperability with external decoder libraries (such as the open-source PyMatching).
  • Custom Python decoders (for investigating new algorithms).

Example setup: 


from loom import decoders, simulate

decoder = decoders.MWPMDecoder.from_code(code)

sim = simulate.Simulator(
    code=code,
    cycle_circuit=cycle_circuit,
    noise_model=noise_model,
    decoder=decoder,
)

results = sim.run(
    p=5e-3,
    n_trials=10_000,
    n_cycles=100,
)
print(results.logical_error_rate)

In advanced research, the focus is usually not on a single data point of \(p_L\), but rather on:

  • Fixing \(d\) and scanning over \(p\) to plot \(p_L\) vs. \(p\) curves.
  • Repeating this for multiple \(d\) and finding the crossing point for threshold estimation.
  • Analyzing the asymptotic slope of \(p_L(p)\) (e.g., \(p_L \sim (p/p_{\text{th}})^{(d+1)/2}\)).

7. Threshold and Scaling Analysis: Experimental Design Across Multiple Code Distances

7.1 Rigorous Definition of Threshold and the Scaling Ansatz

A QEC code family \(\{\mathcal{C}_d\}\) (for example, surface codes of distance \(d=3,5,7,\dots\)) has a threshold \(p_{\text{th}}\) under a given noise model if there exists \(p_{\text{th}} > 0\) such that: \[ \forall\, p < p_{\text{th}}: \quad \lim_{d\to\infty} p_L(p,d) = 0. \] Conversely, if \(p > p_{\text{th}}\), then \(\liminf_{d\to\infty} p_L(p,d) > 0\).

In numerical experiments, it is common to assume that near the threshold the following scaling ansatz holds: \[ p_L(p,d) \approx f\left( (p-p_{\text{th}}) d^{1/\nu} \right), \] where \(\nu\) is the correlation-length critical exponent and \(f\) is some universal scaling function. By scanning \(p\) for fixed \(d\) and then performing a scaling-collapse analysis across different \(d\), one can jointly estimate \(p_{\text{th}}\) and \(\nu\).

7.2 Designing Multi-Distance Code Families and Batch Simulations in el-loom

Planning a full threshold study typically requires:

  1. Selecting a series of distances \(d \in \{d_{\min},\dots,d_{\max}\}\).
  2. Building a code instance \(\mathcal{C}_d\) for each \(d\).
  3. Choosing a grid of physical error rates \(p\in\{p_1,\dots,p_M\}\).
  4. For each \((d,p)\) pair, performing \(N\) Monte Carlo trials to estimate \(p_L(d,p)\).
  5. Storing all results in a unified data structure (for example, a pandas.DataFrame) for analysis.

In el-loom, this can be implemented via loops and configuration files: 


from loom import codes, simulate, decoders

distances = [3, 5, 7]
phys_ps = [2e-3, 3e-3, 4e-3, 5e-3]

records = []

for d in distances:
    code_d = codes.SurfaceCode(distance=d)  # or a custom family generator
    decoder_d = decoders.MWPMDecoder.from_code(code_d)
    sim_d = simulate.Simulator(
        code=code_d,
        cycle_circuit=code_d.default_cycle_circuit(),
        noise_model=noise_model,
        decoder=decoder_d,
    )
    for p in phys_ps:
        res = sim_d.run(
            p=p,
            n_trials=20_000,
            n_cycles=round(d),  # or a more complex choice of T(d)
        )
        records.append({
            "distance": d,
            "p_phys": p,
            "p_log": res.logical_error_rate,
            "stderr": res.stderr,
        })

To mitigate the issue that “near the threshold one needs a very large number of samples,” one often uses adaptive sampling or importance sampling. el-loom may also provide:

  • Automatic stopping criteria based on target confidence intervals.
  • Support for Stim’s efficient statistical interfaces such as --count-logical-errors / --sample.

7.3 Result Analysis and Cross-Validation

Once \(p_L(d,p)\) data are obtained, the mathematical tasks include:

  • Proper error bars (standard errors): \[ \sigma_{p_L} = \sqrt{\frac{p_L(1-p_L)}{N_{\text{trials}}}}. \]
  • Using weighted least-squares fitting to locate the crossing point.
  • Checking whether \(p_{\text{th}}\) is robust under different decoders or noise models.
  • Comparing with theoretical predictions (such as symmetries of self-dual codes, or critical points of corresponding statistical-mechanics models).

8. Custom Code Design Experiments: From Geometry to Code Optimization

8.1 Problem Statement: Designing Optimal Codes for Asymmetric Noise

Consider a concrete research problem:

Given a hardware noise model with far more \(Z\)-errors than \(X\)-errors (e.g., dephasing-dominated noise), we aim to design a stabilizer code that minimizes the long-time logical error rate under a fixed number of qubits.

Mathematically, we parametrize the noise channel as: \[ \mathcal{E}(\rho) = (1-p_Z - p_X)\rho + p_X X\rho X + p_Z Z\rho Z \] and assume \(p_Z \gg p_X\). For a code \(\mathcal{C}\), we can define the “X-type distance” and “Z-type distance”:

  • \(d_X\): the minimum weight of Z-type errors causing a logical \(\overline{X}\) error.
  • \(d_Z\): the minimum weight of X-type errors causing a logical \(\overline{Z}\) error.

Under \(p_Z \gg p_X\), we would like \(d_X \gg d_Z\); that is, we want to increase the distance in the direction of the dominating noise.

8.2 Geometric Design Space and Search Strategies

In el-loom, we can define a parametric code family:

  • Geometric parameters: for example, the aspect ratio \(L_x \times L_y\) of rectangular surface codes.
  • Boundary types: combinations of smooth/rough boundaries.
  • Choice of stabilizers: whether to introduce deformed plaquettes/stars.

For instance, in a rectangular surface code: \[ d_X = L_x, \quad d_Z = L_y \] (depending on the specific choice of boundaries), so under \(p_Z \gg p_X\) we can choose \(L_x \gg L_y\) to optimize performance.

Fig. 5-4: Illustration of rectangular surface code patches with different aspect ratios \(L_x \times L_y\). The logical \(X\) and \(Z\) operators are highlighted as string-like paths, with their lengths corresponding to \(d_X\) and \(d_Z\), respectively, showing that increasing one spatial dimension increases one of the logical distances.
Prompt: Illustration of rectangular surface code patches with different aspect ratios Lx x Ly. Highlight logical X and Z operators as string-like paths, indicating their lengths correspond to d_X and d_Z, respectively. Show that increasing one dimension increases one logical distance.

In el-loom, such a parameterization can be written as: 


def make_rect_surface(Lx, Ly):
    return codes.SurfaceCode(
        size_x=Lx,
        size_y=Ly,
        boundaries=("rough", "smooth"),  # example
    )

# Search for the optimal Lx, Ly under a fixed qubit budget
budget = 100  # qubit budget
candidates = []
for Lx in range(3, 11, 2):
    for Ly in range(3, 11, 2):
        code = make_rect_surface(Lx, Ly)
        if code.n_qubits <= budget:
            candidates.append((code, Lx, Ly))

8.3 Automated Comparative Experiments in el-loom

For each candidate \((L_x,L_y)\) code instance, we can:

  1. Use the same noise model (with asymmetric \(p_Z,p_X\)).
  2. Use a fixed decoder (such as MWPM with anisotropic weights).
  3. Estimate \(p_L\) under a given set of \(p\) or \((p_X,p_Z)\) parameters.
  4. Compare the performance under the same qubit budget.

We can define a cost function, for example: \[ F(\mathcal{C}) = p_L(p_X,p_Z, T; \mathcal{C}), \] which we want to minimize. In el-loom’s Python environment, one could write: 


best = None

for code, Lx, Ly in candidates:
    decoder = decoders.MWPMDecoder.from_code(code)
    sim = simulate.Simulator(
        code=code,
        cycle_circuit=code.default_cycle_circuit(),
        noise_model=noise_model,
        decoder=decoder,
    )
    res = sim.run(
        p=None,  # here p_X, p_Z can be passed directly
        p_X=1e-4,
        p_Z=1e-3,
        n_trials=50_000,
        n_cycles=200,
    )
    score = res.logical_error_rate
    if (best is None) or (score < best["score"]):
        best = {
            "code": code,
            "Lx": Lx,
            "Ly": Ly,
            "score": score,
        }

print("Best aspect ratio:", best["Lx"], best["Ly"], "with p_L=", best["score"])

Such parametric-search experiments have frequently been used in the literature to:

  • Compare the performance of deformed surface codes / XZZX codes.
  • Find optimal tilings under geometric constraints (for example, constraints on the topology of available couplers).
  • Explore fracton-like codes or code structures embedded in a 3D layout.

9. Advanced Topics: Custom Decoders and Data Export

9.1 Exporting Syndrome/Error Histories to External Decoders

Many newer decoders (machine-learning-based, tensor-network-based, etc.) are not natively integrated into el-loom. A typical workflow is:

  1. Use el-loom + Stim to generate syndrome samples.
  2. Export the syndrome time series or graph representations into files (e.g., JSON, HDF5).
  3. Train or run the decoder in an independent environment (PyTorch, JAX).
  4. Return the decoding results or analyze logical error rates offline.

Illustration: 


samples = sim.sample_syndromes(
    n_samples=100_000,
    n_cycles=50,
    return_errors=True,  # also output the actual error operator
)

# Convert samples to NumPy/Tensor
import numpy as np
syndrome_array = np.array(samples["syndromes"])  # shape (N, T, n_stab)
error_labels = np.array(samples["logical_errors"])  # 0/1 per sample

# Save or feed directly into an ML model
np.savez("qec_dataset.npz",
         syndromes=syndrome_array,
         labels=error_labels)

9.2 Custom Python Decoders and the el-loom Interface

If you wish to implement a prototype decoder directly within el-loom, you can implement an interface class such as: 


from loom.decoders import BaseDecoder

class MyCustomDecoder(BaseDecoder):
    def __init__(self, code, params):
        super().__init__(code)
        self.params = params
        # Build syndrome graph, precompute tables, etc. here

    def decode(self, syndrome_history):
        # syndrome_history: shape (T, n_stabilizers)
        # Return a Pauli operator (e.g., textual or binary form)
        # Here, as an illustration, we return the identity (no correction)
        return "I" * self.code.n_qubits

# Usage
decoder = MyCustomDecoder(code, params={...})
sim = simulate.Simulator(..., decoder=decoder)

This interface allows you to:

  • Invoke decode internally from the simulator to obtain the recovery operation for each cycle.
  • Compare different decoder classes on the same code and noise model.
  • Sweep or optimize over decoder parameters \(\theta\).

11. Summary and Directions for Further Work

Starting from the rigorous mathematical definition of stabilizer codes, this lesson has explained how to map them onto el-loom’s data structures and simulation workflows, and has demonstrated a complete pipeline that advanced researchers can use for “custom code design and experimental studies”:

  1. Design or choose a code family, and construct stabilizer and logical-operator representations.
  2. Define the code and layout in el-loom, and generate or customize measurement circuits and schedules.
  3. Model noise channels (including asymmetries, temporal structure, and hardware-specific effects).
  4. Select and implement decoders, and use Monte Carlo simulations to estimate logical error rates.
  5. Design multi-distance, multi-parameter scan experiments for threshold and scaling analysis.
  6. Use parametric search to explore optimal code geometries or structures (such as asymmetric codes).
  7. Export syndromes/data and interface with external ML or tensor-network decoders.
  8. Ensure reproducibility through config-driven experiments and a well-structured project layout.

As next steps, you might:

  • Implement a small but novel custom code (for example, a surface code with dislocations), fully define it in el-loom, and compare its performance.
  • Construct a realistic noise model based on concrete hardware parameters (T1/T2, gate fidelities, readout errors provided by an experimental lab) and re-evaluate the practical threshold of a given code family.
  • Export syndrome histories generated by el-loom, train a neural decoder, and systematically compare it with a traditional MWPM decoder.

As el-loom and its surrounding ecosystem of tools continue to evolve, this workflow can be extended naturally to more complex architectures such as concatenated codes, LDPC codes, and subsystem codes, thereby building a smoother bridge between theory and practice.
