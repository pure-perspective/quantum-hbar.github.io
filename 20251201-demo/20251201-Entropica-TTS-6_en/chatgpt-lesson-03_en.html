1. Surface Code Stabilizers and Measurement Cycles: Mathematics and Intuition

1.1 Review of the Stabilizer Formalism

Consider the Pauli group \( \mathcal{P}_n \) on \(n\) physical qubits: \[ \mathcal{P}_n = \{\pm 1, \pm i\} \times \{I, X, Y, Z\}^{\otimes n}. \] A stabilizer code is defined by an Abelian subgroup \[ \mathcal{S} \subset \mathcal{P}_n, \quad -I \not\in \mathcal{S} \] The code space is \[ \mathcal{C} = \{ \ket{\psi} \in (\mathbb{C}^2)^{\otimes n} \mid S \ket{\psi} = \ket{\psi}, \ \forall S \in \mathcal{S}\}. \] If \( \mathcal{S} \) is generated by \( m \) independent generators \( \{S_1, \dots, S_m\} \), then the code space has dimension \( 2^{n-m} \), and thus we can encode \[ k = n - m \] logical qubits. Logical Pauli operators \( \bar{X}_j, \bar{Z}_j \) are those operators \[ \bar{P} \in \mathcal{P}_n \setminus \mathcal{S} \] that commute with all stabilizers but are not contained in the stabilizer group.

If an error \(E \in \mathcal{P}_n\) anticommutes with some of the stabilizers, then measuring these stabilizers produces a syndrome: \[ S_i E \ket{\psi} = \pm E \ket{\psi}. \] The measurement outcomes \( \pm 1 \) correspond to a binary syndrome string \[ \mathbf{s} = (s_1,\dots,s_m), \quad s_i = \frac{1 - m_i}{2},\quad m_i \in \{+1,-1\}, \] which is the key input for subsequent decoding.

1.2 Geometric Structure of the Surface Code

The surface code can be viewed as a stabilizer code defined on a 2D planar lattice, where physical qubits are placed on edges and stabilizer operators correspond to vertices and plaquettes. The most common variant is the square lattice surface code:

  • Each edge hosts one physical qubit.
  • Each “black” vertex corresponds to an \(X\)-type stabilizer acting on all qubits on the edges incident on that vertex.
  • Each “white” plaquette corresponds to a \(Z\)-type stabilizer acting on all qubits on the edges along the boundary of that plaquette.

For a square patch of distance \(d\), very roughly, the number of physical qubits scales as \(O(d^2)\), and it encodes one logical qubit. The logical operator \( \bar{Z} \) can be realized as a vertical chain of \(Z\) operators spanning the lattice, and \( \bar{X} \) as a horizontal chain of \(X\) operators. This topological structure yields strong fault tolerance against local errors for the surface code.

1.3 Stabilizer Measurement and the Need for Measurement Cycles

In the ideal stabilizer formalism, we “assume” that all stabilizers \(S_i\) can be measured simultaneously and perfectly. However, on real devices and in fine-grained circuit simulations, we must explicitly construct the measurement circuits:

  1. Assign an ancilla qubit to each stabilizer.
  2. Initialize the ancilla to \(\ket{0}\) or \(\ket{+}\) (depending on the stabilizer type).
  3. Use controlled gates (CNOT or variants) to map the error information on the data qubits onto the phase or bit of the ancilla.
  4. Measure the ancilla and read out the syndrome bit.

For example, for a \(Z\)-type stabilizer \[ S_Z = Z_{i_1} Z_{i_2} \cdots Z_{i_w}, \] its measurement circuit can be:

  1. Initialize the ancilla to \(\ket{0}\) (Z-basis).
  2. For each data qubit \(i_j\), apply a CNOT with the data as control and the ancilla as target.
  3. Measure the ancilla in the Z-basis; the outcome \(\pm 1\) is the eigenvalue of \(S_Z\).

For an \(X\)-type stabilizer \[ S_X = X_{i_1} X_{i_2} \cdots X_{i_w}, \] a common procedure is:

  1. Initialize the ancilla to \(\ket{+}\).
  2. For each data qubit \(i_j\), apply a CNOT with the ancilla as control and the data as target.
  3. Measure the ancilla in the X-basis.

These two circuits implement a measurement of the corresponding stabilizer \(S\) in the ideal (noise-free) case. In the presence of noise, however, the ordering of the gates, the layout, and the circuit depth all affect the spatio-temporal propagation of errors, and thus impact decoding and error thresholds. One of the key values of el-loom is precisely its ability to resolve these details at the circuit level.

2. Mathematical Derivation of the Surface Code Stabilizer Structure

2.1 Stabilizer Definitions of the Planar Code

Consider an \(L \times L\) square grid, with edge set \(E\), vertex set \(V\), and face set \(F\). Place one physical qubit on each edge \(e \in E\); the total number of qubits is \[ n = |E|. \] Define:

  • For each vertex \(v \in V\), let \(\partial v \subset E\) be the set of edges incident on that vertex. Define \[ A_v = \prod_{e \in \partial v} X_e. \]
  • For each face \(f \in F\), let \(\partial f \subset E\) be the set of edges along the boundary of that face. Define \(B_f\) equals the product over edges \(e\) in the boundary of \(f\) of \(Z_e\).-->\[ B_f = \prod_{e \in \partial f} Z_e. \]

One can check that all \(A_v\) mutually commute, all \(B_f\) mutually commute, and any \(A_v\) commutes with any \(B_f\) (with some care for the case of sharing an odd number of edges; with appropriate boundary conditions for the planar code, commutativity is preserved). The full stabilizer group is \[ \mathcal{S} = \langle \{A_v\}_{v \in V'}, \{B_f\}_{f \in F'} \rangle, \] where \(V'\) and \(F'\) are generator sets after removing linear dependencies. For the planar code, we ultimately obtain \(k=1\) logical qubit.

2.2 Commutation Relations and the Structure of Syndromes

Given a Pauli error \[ E = \bigotimes_{e \in E} E_e, \qquad E_e \in \{I,X,Y,Z\}, \] its syndrome is \[ s_v = \begin{cases} 0, & A_v E = E A_v,\\ 1, & A_v E = - E A_v, \end{cases} \quad s_f = \begin{cases} 0, & B_f E = E B_f,\\ 1, & B_f E = - E B_f. \end{cases} \] More concretely, if \(E\) contains a \(Z\) or \(Y\) error on some edge \(e\), then it anticommutes with the corresponding vertex operators \(A_v\) at adjacent vertices, giving rise to flipped “X syndromes”; if it contains an \(X\) or \(Y\) error, then the syndromes \(B_f\) on adjacent faces are flipped. This leads to the classical graph-theoretic picture of “error chains” and “defect endpoints”.

From the time-series perspective, we perform multiple rounds of syndrome measurements, obtaining \[ \mathbf{s}^{(t)} = \left( \{s_v^{(t)}\}_{v \in V}, \{s_f^{(t)}\}_{f \in F} \right), \quad t = 1, \dots, T. \] Even when the measurements themselves are faulty, by considering the time dimension appropriately, the overall structure can still be mapped to a three-dimensional (2D space + 1D time) error graph and decoded using algorithms such as minimum-weight perfect matching (MWPM). This is precisely the focus of circuit-level surface code simulations: not only the spatial structure but also an explicit time axis must be present.

3. Equivalence of Measurement Circuits and Noise Propagation

3.1 Equivalent Circuits for Measuring a Single Stabilizer

Take a \(Z\)-type stabilizer \[ S_Z = Z_1 Z_2 Z_3 Z_4 \] as an example. Its measurement circuit can be realized in multiple ways, as long as \[ M_Z^{(\text{anc})} \circ \mathcal{U} (\rho \otimes \ket{0}\!\bra{0}) = \sum_{m = \pm 1} \Pi_m \rho \Pi_m \otimes \ket{m}\!\bra{m}, \] where \(\Pi_m\) is the projector associated with \(S_Z\). The standard approach is:

  1. Initialize ancilla \(a\) to \(\ket{0}\).
  2. Apply four CNOTs in sequence: \[ \text{CNOT}_{1 \to a},\ \text{CNOT}_{2 \to a},\ \text{CNOT}_{3 \to a},\ \text{CNOT}_{4 \to a}. \]
  3. Measure the ancilla in the Z-basis to obtain \(m = \pm 1\).

In the ideal (noise-free) setting, the group-theoretic action of CNOT can be formalized as: \[ \text{CNOT}_{i \to a}: \begin{cases} Z_i \mapsto Z_i,\\ Z_a \mapsto Z_i Z_a, \end{cases} \quad \Rightarrow Z_a \mapsto Z_1 Z_2 Z_3 Z_4 Z_a \] after composing the four CNOTs. Therefore \[ Z_a^{(\text{final})} = S_Z \cdot Z_a^{(\text{initial})}. \] If the ancilla is initially in the \(+1\) eigenstate, \(Z_a \ket{0} = \ket{0}\), then measuring the final Z eigenvalue of the ancilla yields the eigenvalue of \(S_Z\).

3.2 Error Propagation in the Presence of Noise

With noise present, a two-qubit CNOT gate can be modeled as an ideal CNOT \(U_{\text{CNOT}}\) followed by a noisy channel \(\mathcal{N}\): \[ \mathcal{E}(\rho) = \mathcal{N} \bigl( U_{\text{CNOT}} \rho U_{\text{CNOT}}^\dagger \bigr). \] If we adopt a Pauli-channel approximation, for example a two-qubit random Pauli error, \[ \mathcal{N}(\rho) = (1-p)\rho + \sum_{P \in \{X,Y,Z\}^{\otimes 2}} p_P P\rho P, \quad \sum_P p_P = p, \] then we can analyze the propagation of Pauli errors through the circuit in the Heisenberg picture; for example, an \(X\) error on the control qubit after a CNOT evolves as: \[ X_c \mapsto X_c X_t, \] so an \(X\) error can propagate from the data qubit to the ancilla. These propagation paths are precisely the source of the time-correlated structure of the syndromes.

In the surface code, measuring each stabilizer requires one ancilla, and in order to prevent measurement circuits of different stabilizers from interfering with one another, the CNOT timing and scheduling must be carefully designed. In el-loom, such timing designs are concretely reflected in the implementation of “layers” and “cycles”.

3.3 Repeated Measurement Cycles and the Time Dimension

In realistic fault-tolerant computation scenarios, we perform repeated rounds of syndrome measurements \[ t = 1, 2, \dots, T, \] where each round includes the measurement of all vertex and face stabilizers. For implementation convenience, each round is often given a fixed gate ordering and schedule. Formally, we can define a “measurement cycle superoperator”: \[ \mathcal{M} = \mathcal{M}_{\text{readout}} \circ \mathcal{U}_{\text{noise+gates}}, \] where \(\mathcal{M}_{\text{readout}}\) comprises the ancilla measurements and the recording of the corresponding classical outcomes. After \(T\) rounds of measurement, the overall evolution is \[ \rho^{(T)} = \bigl(\mathcal{M}\bigr)^T(\rho^{(0)}), \] while simultaneously producing the list of syndromes \[ \{\mathbf{s}^{(t)}\}_{t=1}^T. \] This is a typical “measurement cycle simulation” task in el-loom: given the initial state, the noise model, and the measurement circuit, generate the syndrome time series and the final logical state (or logical error events) after many cycles.

4.2 Using a Pre-Built Surface Code Family

el-loom typically provides a surface code family, such as planar codes of distance \(d\). Conceptually, one can do: 

from loom.codes import SurfaceCode

d = 3  # code distance
code = SurfaceCode(distance=d, boundary='planar')

Internally, this constructs:

  • Data qubits: corresponding to lattice edges.
  • Ancilla qubits: corresponding to each X-/Z-type stabilizer.
  • Stabilizer generator data structures, including:
    • Type (X or Z stabilizer).
    • The list of data qubits it acts on.
    • Ancilla qubit index.

If researchers need deformed lattices (e.g., rotated surface codes, heavy-hex codes, etc.), they can use the lower-level el-loom API to define the geometry relating qubits and checks directly. This is quite important in advanced research because the actual hardware topology is rarely a perfect square lattice.

4.3 Manually Defining a Minimal Surface Code Example

To illustrate how to exert fine control over the structure in el-loom, we demonstrate how to manually define a minimal distance-3 planar code patch (for teaching purposes only; in practice, refer to the official documentation for exact API names). Suppose we have:

  • Data qubits labeled by integer indices 0, 1, 2, 3, ...
  • Ancilla qubits labeled by integer indices 100, 101, ...
  • Stabilizers represented by an object Stabilizer.
from loom.lattice import Lattice, Stabilizer

lat = Lattice()

# Add data qubits
data_ids = [0, 1, 2, 3, 4, 5, 6]  # example
for q in data_ids:
    lat.add_data_qubit(q)

# Add ancilla qubits
ancilla_x = [100, 101, 102]
ancilla_z = [200, 201, 202]
for q in ancilla_x + ancilla_z:
    lat.add_ancilla_qubit(q)

    kind='Z',
    data_support=[0, 1, 3, 4],
    ancilla=200
)
lat.add_stabilizer(stab_z0)

# Similarly add other X-/Z-stabilizers
...

In an actual el-loom implementation, the Lattice object may contain much richer structure, such as:

  • Coordinates (x, y) of the qubits, for visualization and mapping to hardware.
  • Time-slot information, for automatically generating CNOT schedules.
  • Special boundary-type annotations for rotated / dislocation / twist variants of the surface code.

5. Constructing Measurement Cycles in el-loom

5.1 Abstract Description of a Measurement Cycle

At an abstract level, one round of a surface code measurement cycle consists of:

  1. Initializing all ancilla qubits:
    • Ancillas for X-stabilizers are initialized to \(\ket{+}\).
    • Ancillas for Z-stabilizers are initialized to \(\ket{0}\).
  2. Applying a sequence of CNOTs to each stabilizer according to a fixed schedule:
    • For Z-stabilizers: CNOT(data → ancilla).
    • For X-stabilizers: CNOT(ancilla → data).
  3. Measuring all ancillas:
    • Ancillas of Z-stabilizers are measured in the Z-basis.
    • Ancillas of X-stabilizers are measured in the X-basis (equivalently, apply a Hadamard before and after a Z-basis measurement).

In el-loom, this is typically encapsulated in a “cycle object” or “measurement round” description, which is then translated to a low-level sequence of gates (a gate list or circuit object). For example (schematically): 

from loom.circuits import MeasurementCycleBuilder

builder = MeasurementCycleBuilder(lattice=lat)

cycle = builder.build_standard_surface_code_cycle(
    schedule='canonical',  # or 'checkerboard', custom, etc.
)

Here the schedule parameter determines the time slots of the CNOTs, ensuring that no qubit participates in more than one gate at the same time, while keeping the total circuit depth as low as possible. For standard square lattice surface code implementations, 4-step or 8-step CNOT schedules are commonly used.

5.2 Circuit-Level Implementation: Initialization, Gates, and Measurement

At a lower-level API, one cycle can be described as a sequence of gate operations, for example: 

from loom.circuits import Circuit

circ = Circuit()

# 1. Initialize ancillas
for q in ancilla_z:
    circ.add_reset(q, basis='Z')  # |0>
for q in ancilla_x:
    circ.add_reset(q, basis='X')  # |+>, often implemented as |0> then H

# 2. CNOT scheduling
for timeslot in schedule:
    for (ctrl, tgt) in timeslot.cnot_pairs:
        circ.add_cnot(ctrl, tgt)

# 3. Measure ancillas
for q in ancilla_z:
    circ.add_measure(q, basis='Z')
for q in ancilla_x:
    circ.add_measure(q, basis='X')

In the surface code, one typically arranges that stabilizers of the same type (e.g., all X-stabilizers or all Z-stabilizers) share the same “CNOT layer structure”. For standard surface codes, el-loom usually provides a default schedule, which researchers only need to override or extend when necessary.

5.3 Mathematically Verifying the Correctness of a Measurement Cycle

For any fixed cycle circuit \(C\), we want it to implement, in the ideal case, the POVM \[ \{ \Pi_{\mathbf{s}} \}_{\mathbf{s} \in \{0,1\}^m} \] where each element is \[ \Pi_{\mathbf{s}} = \prod_{i=1}^m \frac{1}{2}(I + (-1)^{s_i} S_i), \] with \(S_i\) being the stabilizer generators. That is:

  1. If the initial state \(\rho\) lies in the code space (all \(S_i = +1\)), then ideally the probability of observing syndrome \(\mathbf{s} = \mathbf{0}\) is 1.
  2. If an error \(E\) acts on \(\rho\) and causes some stabilizers \(S_i\) to anticommute, then the resulting syndrome distribution exactly reflects the support of \(E\).

In the circuit model, a measurement cycle defines the quantum channel \[ \mathcal{M}(\rho) = \sum_{\mathbf{s}} \mathrm{Tr}_a [\mathcal{K}_{\mathbf{s}} (\rho \otimes \ket{0}\!\bra{0}^{\otimes m})] \otimes \ket{\mathbf{s}}\!\bra{\mathbf{s}}, \] where \(\mathcal{K}_{\mathbf{s}}\) encapsulates the unitary evolution plus projection for outcome \(\mathbf{s}\). If the CNOT schedule is non-interfering (for example, if the order in which different stabilizers act on the same data qubit only changes a local phase in the ideal case), then one can show that: \[ \Pi_{\mathbf{s}} = \mathrm{Tr}_a \left[ K_{\mathbf{s}}^\dagger K_{\mathbf{s}} \right], \] where \(K_{\mathbf{s}}\) is the Kraus operator corresponding to outcome \(\mathbf{s}\). This proves that the measurement cycle corresponds to the ideal stabilizer measurement POVM.

In the implementation of el-loom, we can verify this by:

  • Performing full state-vector or density-matrix simulations for small codes.
  • Checking whether the syndrome distributions under ideal conditions match theoretical predictions.

For a minimal distance-3 example, one can sample 100 random code states, apply random single-qubit Pauli errors \(E \in \{I,X,Y,Z\}\), perform one measurement cycle, and check whether the resulting syndrome matches the “endpoint” structure associated with \(E\). Doing so helps verify the correctness of the cycle structure implemented in el-loom.

6. Adding Noise in el-loom: Circuit-Level Noise Models

6.1 Structure of Noise Models

el-loom provides a variety of noise model components, which can be conceptually decomposed into:

  • Single-qubit gate noise: e.g., apply a Pauli channel after every 1-qubit gate.
  • Two-qubit gate noise: e.g., apply a two-qubit depolarizing channel after every CNOT.
  • Idle / decoherence noise: apply noise induced by \(T_1/T_2\) during idle time slots.
  • Measurement errors: classical readout flips or non-ideal projective measurements.

Mathematically, noise can be described using Kraus operators or superoperators. For the commonly used two-qubit depolarizing channel, we have: \[ \mathcal{D}_p^{(2)}(\rho) = (1-p)\rho + \frac{p}{15} \sum_{P \in \mathcal{P}_2 \setminus \{II\}} P\rho P. \] This can approximate the noise of a CNOT gate in real hardware. el-loom associates this with a specific gate to form a noisy gate model:

\[ \tilde{\mathcal{U}}_{\text{CNOT}}(\rho) = \mathcal{D}_p^{(2)}\bigl( U_{\text{CNOT}} \rho U_{\text{CNOT}}^\dagger \bigr). \]

6.2 Configuring Noise Models in el-loom

In code, one typically first creates a noise configuration and then attaches it to the circuit simulator, for example: 

from loom.noise import NoiseModel

noise = NoiseModel()

# Single-qubit gate noise
noise.set_1q_gate_noise(
    p=1e-4,  # error probability
    model='depolarizing'
)

# Two-qubit gate noise (e.g., CNOT)
noise.set_2q_gate_noise(
    p=5e-3,
    model='depolarizing'
)

# Measurement error: readout bit-flip
noise.set_measurement_noise(
    p=1e-3,
    model='bitflip'
)

# Idle noise / T1T2
noise.set_idle_noise(T1=50e-6, T2=60e-6, gate_time=20e-9)

Then, for running measurement-cycle simulations: 

from loom.sim import CircuitSimulator

sim = CircuitSimulator(noise_model=noise)

# Build measurement cycle circuit
cycle = builder.build_standard_surface_code_cycle(...)

# Run T rounds
T = 20
syndrome_records = []
state = code.initial_state()  # or logical |0_L>, etc.

for t in range(T):
    result = sim.run(cycle, init_state=state)
    syndrome_records.append(result.syndrome)
    state = result.final_state  # optional, if tracking full state

For large codes or long time series, fully tracking the density matrix or state vector is too costly; el-loom typically employs more efficient techniques such as Pauli frame tracking or stabilizer simulation. Mathematically, many standard noise models (Pauli channels) are closed under Clifford circuits (the stabilizer formalism is closed under Clifford gates and Pauli noise), allowing the tracking of syndromes and the evolution of logical operators with complexity \(O(n^3)\) or better.

6.3 Statistical Properties of Syndrome Time Series

In the presence of noise, the observed syndrome \(\mathbf{s}^{(t)}\) no longer depends solely on data-qubit errors; measurement and ancilla errors also contribute “noise” to the syndrome. Ideally, for each measurement round we have: \[ \mathbf{s}^{(t)} = \mathbf{s}_{\text{data}}^{(t)} \oplus \mathbf{s}_{\text{meas}}^{(t)}, \] where \(\mathbf{s}_{\text{data}}^{(t)}\) is determined by data-qubit errors accumulated over the current and previous rounds, and \(\mathbf{s}_{\text{meas}}^{(t)}\) captures “false positives” caused by measurement / ancilla errors. In the time dimension, typical decoders use space–time graph structures; for example, 3D MWPM treats changes in the syndrome as “defect endpoints” and performs matching in space–time.

In el-loom, we can directly access the syndrome for each round: 

# syndrome_records[t][i]: i-th stabilizer outcome at round t

These syndromes can then be fed to external decoders (such as the Python interface of PyMatching). Here, el-loom mainly provides accurate syndrome time series that incorporate circuit-level noise.

7. Example Implementation of a Surface Code Measurement Cycle: Distance-3 Planar Code

Below we present a relatively concrete end-to-end workflow example: on a distance-3 planar surface code, we construct a standard measurement cycle and noise model, and perform multi-round syndrome simulations. (Note: actual class and function names should be taken from the official documentation; what follows is pedagogical pseudo-API.)

7.1 Building the Code and Lattice

from loom.codes import SurfaceCode
from loom.circuits import MeasurementCycleBuilder
from loom.noise import NoiseModel
from loom.sim import CircuitSimulator

# 1. Build a distance-3 planar surface code
d = 3
code = SurfaceCode(distance=d, boundary='planar')

lattice = code.lattice
data_qubits = lattice.data_qubits()
ancilla_x = lattice.ancilla_x()
ancilla_z = lattice.ancilla_z()

7.2 Building a Standard Measurement Cycle

# 2. Build the surface code measurement cycle
builder = MeasurementCycleBuilder(lattice=lattice)
cycle = builder.build_standard_surface_code_cycle(
    schedule='canonical_4step'
)

Here, canonical_4step denotes a 4-layer CNOT schedule in which each stabilizer interacts with one of its data qubits in each layer, ensuring:

  • No qubit participates in two gates during the same time step.
  • Good symmetry, facilitating the analysis of error propagation.

Suppose we want to simulate the behavior of the logical state \(\ket{\bar{0}}\) under \(T\) rounds of measurement cycles. We can choose the initial state to be \[ \rho^{(0)} = \ket{\bar{0}}\!\bra{\bar{0}}. \] In el-loom, there may be an API for directly building logical states: 

state = code.logical_state('0')  # or code.encode(|0> logical)
T = 30

logical_flips = []

for t in range(T):
    result = sim.run(cycle, init_state=state)
    syndrome_records.append(result.syndrome)
    state = result.final_state

    # Optionally: after each round, test the expectation of logical Z
    # to estimate whether a logical X error has occurred
    exp_ZL = code.expect_logical_Z(state)

    logical_flips.append(1 if exp_ZL < 0 else 0)

8. In-Depth: Effects of Cycle Structure on Error Thresholds and Comparative Experiments in el-loom

8.1 Comparing Different Measurement Cycle Schemes

In theory, as long as a circuit correctly implements the stabilizer measurement POVM, different cycle schemes are equivalent in the absence of noise. However, in realistic noisy settings:

  • Different schedules can give rise to different error propagation paths (e.g., hook errors).
  • Some designs can reduce the extent to which a single-qubit error spreads into weight-2 or higher-weight correlated errors.
  • Certain schemes allow local modifications to better respect hardware connectivity constraints.

These differences directly manifest in the logical error rates and threshold estimates. el-loom is an ideal tool for such comparisons: we can implement multiple cycle variants, simulate them under the same noise model, and compare their logical failure probabilities.

8.2 Implementing Multiple Cycles and Comparing Them in el-loom

Suppose we have two different CNOT schedules:

  • schedule='canonical_4step'
  • schedule='optimized_hook_suppression'

We can construct two cycles as follows: 

cycle_A = builder.build_standard_surface_code_cycle(
    schedule='canonical_4step'
)
cycle_B = builder.build_standard_surface_code_cycle(
    schedule='optimized_hook_suppression'
)

Then, for the same distance \(d\), noise strength \(p\), and number of rounds \(T\), we estimate the logical failure rate: 

def estimate_logical_failure(cycle, trials=1000, T=30):
    failures = 0
    for _ in range(trials):
        state = code.logical_state('0')
        all_syndromes = []
        for t in range(T):
            res = sim.run(cycle, init_state=state)
            all_syndromes.append(res.syndrome)
            state = res.final_state
        # Decode and check for logical error
        if has_logical_error(all_syndromes):
            failures += 1
    return failures / trials

pA = estimate_logical_failure(cycle_A)
pB = estimate_logical_failure(cycle_B)

print("Canonical schedule logical error rate:", pA)
print("Optimized schedule logical error rate:", pB)

Here, has_logical_error denotes an external or built-in decoder. In practice, one can feed the syndromes to an MWPM decoder to obtain an estimated error chain \(\hat{E}\) and then check whether \(\hat{E} E\) contains a nontrivial logical operator (e.g., \(\bar{X}\) or \(\bar{Z}\)).

8.3 Mathematical Understanding of Hook Error Suppression

So-called hook errors refer to situations where, due to a particular CNOT scheduling pattern, a single physical error (for example, an error on an ancilla) is propagated through multiple CNOT gates onto several data qubits, forming a “hook-shaped” error chain whose weight may approach or equal the code distance, thus making it more difficult for the decoder to detect.

Formally, if an \(X_a\) error occurs on an ancilla \(a\), and we perform two consecutive CNOTs (with \(a\) as control and \(d_1, d_2\) as targets): \[ X_a \xrightarrow{\text{CNOT}_{a\to d_1}} X_a X_{d_1} \xrightarrow{\text{CNOT}_{a\to d_2}} X_a X_{d_1} X_{d_2}. \] Further entanglement with other CNOTs can lead to weight-3 or even higher-weight correlated errors. By carefully designing the schedule to ensure that a given Pauli error only propagates within a “short range”, one can suppress hook errors to some extent and thereby improve the threshold.

el-loom allows us to inject a single Pauli error precisely at the circuit level and track its final effect. For example: 

from loom.debug import inject_pauli_error

cycle_hook_test = builder.build_standard_surface_code_cycle(
    schedule='candidate_schedule'
)

# Inject an X error on ancilla q at a specific time step t0
inj_cycle = inject_pauli_error(cycle_hook_test, qubit=q, pauli='X', time=t0)

res = sim.run(inj_cycle, init_state=code.logical_state('0'),
              noise_model=None)  # no additional noise

final_pauli = analyze_final_error(res)
print("Effective weight of propagated error:", final_pauli.weight())

In this way we can compare hook-error propagation behavior under different schedules and use it to optimize the measurement cycle both theoretically and in practice.

9. Summary and Further Extensions

Starting from the stabilizer formalism and the topological structure of the surface code, this lesson derived the mathematical foundations of surface code stabilizer measurements and measurement cycles, explained how to implement these measurement circuits at the circuit level, and then introduced how to use el-loom to:

  • Build the surface code lattice and stabilizer structure.
  • Construct standard measurement cycles.
  • Define circuit-level noise models (1-qubit, 2-qubit, measurement, idle).
  • Run multi-round syndrome measurement simulations and obtain time series data.
  • Compare different measurement cycle designs in terms of logical error rates and analyze hook errors.

For PhD students and researchers, the main value of el-loom in surface code studies lies in:

  1. A bridge from abstract codes to concrete circuits: it can automatically translate high-level stabilizer descriptions into executable circuits and measurement cycles.
  2. Flexible noise modeling: it supports a variety of physical dynamics and noise sources, making it easy to match real device parameters.
  3. Integration with decoders: it can output syndrome time series to specialized decoders for threshold and fault-tolerance architecture studies.
  4. Extensible lattices and code families: it can implement modern architectures such as rotated surface codes and heavy-hex codes.

Recommended directions for further exploration include:

  • Implementing rotated surface codes and XZZX codes in el-loom and comparing their performance under biased noise.
  • Integrating custom scheduling strategies (e.g., minimizing hook errors, respecting hardware connectivity) into the MeasurementCycleBuilder.
  • Building more physically realistic noise models for specific hardware platforms (such as superconducting qubits and ion traps), including non-Markovian effects or leakage errors.
  • Connecting el-loom to higher-level fault-tolerant schemes (such as lattice surgery and magic state distillation) to perform end-to-end fault-tolerance cost estimates.
