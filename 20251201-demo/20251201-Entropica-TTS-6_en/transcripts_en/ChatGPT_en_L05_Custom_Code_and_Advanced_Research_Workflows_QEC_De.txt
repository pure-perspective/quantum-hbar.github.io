1. QEC Research Workflow and the Role of el-loom

1.1 Typical QEC Research Problems

Common research questions in the QEC field at the PhD and advanced-research level include:

 Designing new stabilizer codes tailored to specific hardware constraints (coupling graph, decoherence mechanisms, measurement frequency).

 Re-evaluating thresholds of known codes (e.g., surface code, color code) under asymmetric noise or realistic hardware noise.

 Studying the performance of new types of decoders (neural decoder, tensor-network decoder, belief propagation, etc.).

 Designing custom measurement schedules and gate schedules, and analyzing the impact of rounding errors and time-correlated noise.

 Comparing different code families in terms of asymptotic scaling of the logical error rate.

These problems share a common requirement: to rapidly and systematically turn “abstract code structure + noise model” into “reproducible numerical experiments.” The el-loom package is a Python toolkit designed exactly for this purpose, with an emphasis on:

 A unified abstraction for stabilizer codes and measurement circuits.

 Integration with efficient simulators such as stim for large-scale Monte Carlo simulations.

 Support for multiple decoders and output formats, facilitating downstream data analysis.

5.2 Custom Measurement Schedules in el-loom

el-loom typically provides two strategies:

 Automatically generated schedules: Based on the supports of stabilizers and the layout, it attempts to generate conflict-free circuits with minimal depth.

 Manually specified schedules: Researchers can explicitly define multiple rounds of CNOTs and ancilla usage to finely control the structure of error propagation.

An example of manual specification:

from loom import circuits

builder = circuits.CircuitBuilder(code)

# Design a measurement circuit for some Z-type stabilizer S_1
anc = builder.new_ancilla(init="0")

# round 1: CNOTs on disjoint pairs
builder.cnot(control=0, target=anc) # Z on data 0
builder.cnot(control=3, target=anc) # Z on data 3

# round 2: next layer
builder.cnot(control=1, target=anc)
builder.cnot(control=4, target=anc)

# measure ancilla in Z
builder.measure(anc, basis="Z")

syndrome_circuit = builder.to_circuit()

Using such a builder interface, you can:

 Avoid multiple ancillas simultaneously interacting with neighboring qubits (reducing correlated errors).

 Optimize circuit depth (taking into account T1/T2 decoherence).

 Insert idle-gate noise models.

This “local stabilizer measurement circuit” can then be replicated for all faces/stars to form a complete cycle.

9. Advanced Topics: Custom Decoders and Data Export

9.1 Exporting Syndrome/Error Histories to External Decoders

Many newer decoders (machine-learning-based, tensor-network-based, etc.) are not natively integrated into el-loom. A typical workflow is:

 Use el-loom + Stim to generate syndrome samples.

 Export the syndrome time series or graph representations into files (e.g., JSON, HDF5).

 Train or run the decoder in an independent environment (PyTorch, JAX).

 Return the decoding results or analyze logical error rates offline.

Illustration:

samples = sim.sample_syndromes(
 n_samples=100_000,
 n_cycles=50,
 return_errors=True, # also output the actual error operator
)

# Convert samples to NumPy/Tensor
import numpy as np
syndrome_array = np.array(samples["syndromes"]) # shape (N, T, n_stab)
error_labels = np.array(samples["logical_errors"]) # 0/1 per sample

# Save or feed directly into an ML model
np.savez("qec_dataset.npz",
 syndromes=syndrome_array,
 labels=error_labels)

11. Summary and Directions for Further Work

Starting from the rigorous mathematical definition of stabilizer codes, this lesson has explained how to map them onto el-loom’s data structures and simulation workflows, and has demonstrated a complete pipeline that advanced researchers can use for “custom code design and experimental studies”:

 Design or choose a code family, and construct stabilizer and logical-operator representations.

 Define the code and layout in el-loom, and generate or customize measurement circuits and schedules.

 Model noise channels (including asymmetries, temporal structure, and hardware-specific effects).

 Select and implement decoders, and use Monte Carlo simulations to estimate logical error rates.

 Design multi-distance, multi-parameter scan experiments for threshold and scaling analysis.

 Use parametric search to explore optimal code geometries or structures (such as asymmetric codes).

 Export syndromes/data and interface with external ML or tensor-network decoders.

 Ensure reproducibility through config-driven experiments and a well-structured project layout.

As next steps, you might:

 Implement a small but novel custom code (for example, a surface code with dislocations), fully define it in el-loom, and compare its performance.

 Construct a realistic noise model based on concrete hardware parameters (T1/T2, gate fidelities, readout errors provided by an experimental lab) and re-evaluate the practical threshold of a given code family.

 Export syndrome histories generated by el-loom, train a neural decoder, and systematically compare it with a traditional MWPM decoder.

As el-loom and its surrounding ecosystem of tools continue to evolve, this workflow can be extended naturally to more complex architectures such as concatenated codes, LDPC codes, and subsystem codes, thereby building a smoother bridge between theory and practice.
